Build a complete, functional, mobile-first application called **AquaWise — Weather-Aware Irrigation Decision Support**.

### 1. Objective

Create a polished, installable Progressive Web App (PWA) for Android phones that helps farmers decide whether to water their crops.

The main recommendation must be one of:

- **WATER NOW**
- **WAIT**
- **CHECK FIELD**

The app must explain the recommendation in simple language.

**IMPORTANT: Software-only version. Do not implement or depend on any hardware.** No ESP32, Arduino, sensors, pumps, servos, buzzers, OLED displays, MQTT hardware connections, or physical device controls. All field readings and irrigation operations must be simulated. Structure the application so real hardware can be integrated later without rewriting the frontend.

### 2. Technology stack

Use:
- Frontend: React, TypeScript and Vite.
- Styling: Tailwind CSS or an equivalent consistent styling system.
- Backend: Python with FastAPI.
- Database: SQLite.
- Charts: Recharts or an equivalent React charting library.
- ML: Python scikit-learn where appropriate.
- Live updates: WebSocket or Server-Sent Events.
- PWA: Web app manifest, service worker, install support and offline app-shell caching.

Keep the frontend and backend in a single Replit project if the environment supports running both reliably. Configure the application to run through Replit's supported workflow. Do not leave the backend as pseudocode or replace it with hardcoded frontend-only logic.

### 3. Design requirements

Create a professional agricultural technology interface that feels like a real product.

- Mobile-first, responsive design optimized for Android phones.
- Clean green-and-white palette, muted natural backgrounds, readable typography and clear visual hierarchy.
- Large touch targets, accessible contrast, rounded cards and restrained use of shadows.
- A simple bottom navigation bar on mobile.
- Desktop layout should also work well.
- Use appropriate icons, polished charts, useful empty states, loading states and error messages.
- Avoid excessive gradients, clutter, generic landing-page sections and decorative elements that obstruct usability.

The primary screen must prioritize the recommendation and the next action, not charts or technical metrics.

### 5. Decision engine

Implement a deterministic, testable Python rules engine in the FastAPI backend.

Use configurable dry and wet calibration points. Calculate:
- Low-moisture threshold = dry point + 25% of the dry-to-wet range.
- Target moisture = dry point + 70% of the dry-to-wet range.

Apply the rules in this order:
1. If soil moisture is invalid and there is no reliable estimate, return CHECK FIELD.
2. If it is raining now, return WAIT.
3. If moisture is below the low threshold and meaningful rain is not forecast soon, return WATER NOW.
4. If moisture is below the low threshold but rain is expected soon, return WAIT and explain why.
5. If moisture is sufficient, return WAIT.
6. If a credible moisture forecast predicts that the field will become too dry later, provide an estimated watering time.

Meaningful forecast rain means probability of at least 60% and rainfall amount of at least 2 mm within the next 6 hours.

Each recommendation must include a status, localized explanation, confidence, ranked decision factors, input data sources and suggested duration where relevant.

Always preserve a rule-based fallback if the ML service fails.

### 6. Weather integration

Integrate a free weather forecast API, preferably Open-Meteo, using a configurable field location.

Show forecast rain probability, precipitation and temperature. Cache the latest successful forecast. If the service fails, use cached information, mark it stale and reduce recommendation confidence appropriately.

Provide a labelled Test Mode that allows the user to simulate current rain, soil dryness, upcoming rainfall and sensor faults. Clearly distinguish overrides from real weather data.

Do not require API keys for a provider that does not need them. Handle unavailable weather data gracefully.

### 7. Simulated irrigation controls

Implement functional software-only controls:
- Start irrigation manually for a selected duration.
- Stop an active simulated watering session immediately.
- Automatically expire sessions when the duration ends.
- Advisory mode only recommends watering.
- Auto mode starts a simulated watering session when WATER NOW is returned with at least Medium confidence.
- Stop any automatic session when rain begins, the target moisture is reached, or the maximum duration is reached.
- Record every start and stop with its source.
- Prevent multiple conflicting active sessions.
- Enforce the maximum run duration in the backend.

Clearly label these as simulated operations. Never imply that a physical pump is running.

### 8. Moisture forecasting and ML

Implement a practical, lightweight forecasting approach.

- Use a soil-water-balance simulator to generate synthetic training sequences when historical field data is unavailable.
- Train a scikit-learn gradient-boosting regression model, or another appropriate lightweight tree-based regressor, to predict future soil moisture.
- Include recent moisture, time, temperature, humidity, sunlight, rain, forecast rainfall and simulated irrigation history as features where available.
- Evaluate against a persistence baseline on held-out data.
- Use the ML forecast only if it beats the baseline under a clearly defined evaluation metric; otherwise use the simulator or persistence fallback.
- Clearly label forecasts as experimental when based on synthetic data.

Implement schedule comparisons using a common simulation model and transparent assumptions. Do not fabricate accuracy scores.

Implement basic sensor-fault detection and missing-moisture estimation using recent readings, drying trends, weather and simulated irrigation history. Label estimated values and lower confidence as the estimate ages.

Structure the learning code so retraining, model versioning and conditional promotion can be added cleanly. Do not pretend that a production-grade self-learning pipeline exists if it has not been implemented.
